# 경제시황분석 브리핑 뷰어

Google Drive의 "경제시황분석 - Claude" 폴더에 있는 마크다운 브리핑 파일들을 목록으로 보여주고,
클릭하면 본문을 보기 좋게 렌더링해주는 정적 웹페이지입니다.
백엔드 서버 없이 GitHub Pages로만 배포됩니다.

## 동작 방식

- 방문자가 "Google로 로그인" 버튼으로 **본인 구글 계정**으로 로그인합니다(브라우저 안에서만 처리, 서버 없음).
- 로그인 후 브라우저가 Google Drive API를 직접 호출해 폴더 안의 `.md` 파일 목록을 가져옵니다.
- 목록에서 파일을 클릭하면 원문을 가져와 마크다운으로 렌더링합니다.
- 드라이브 폴더는 비공개로 유지해도 되며, 로그인한 계정에 접근 권한이 있을 때만 내용이 보입니다.
- 모바일 화면에서는 목록이 좌측 슬라이드 메뉴(햄버거 버튼 ☰)로 표시됩니다.
- 하위 폴더 탐색은 `config.js`의 `OWNER_EMAIL`로 지정한 계정으로 로그인했을 때만 표시됩니다.
  다른 테스트 사용자 계정으로 로그인하면 최상위 폴더의 `.md` 파일만 보입니다.
- PWA(설치형 웹앱)로 동작합니다. 모바일/데스크톱 브라우저에서 "홈 화면에 추가" 또는
  "앱 설치"로 아이콘을 만들어 일반 앱처럼 실행할 수 있습니다.
- 로그인은 백엔드 없이 가능한 한 오래 유지되도록 처리했습니다: 브라우저에 구글 로그인
  세션이 남아있는 동안은 페이지를 다시 열어도 자동으로(조용히) 재로그인을 시도하고,
  액세스 토큰이 만료되기 전에 미리 갱신합니다. 다만 이건 진짜 "무기한 로그인"은 아닙니다 —
  구글이 백엔드 없는 앱에는 refresh token을 내주지 않기 때문에, 브라우저에서 구글
  계정을 완전히 로그아웃하거나 이 앱에 대한 접근 권한을 취소하면 다시 로그인 버튼을
  눌러야 합니다. (아래 "로그인 유지의 한계" 참고)

## 배포 전 필수 설정: Google OAuth 클라이언트 ID 발급

이 저장소의 코드만으로는 동작하지 않습니다. 아래 절차로 본인 소유의 OAuth 클라이언트 ID를 발급받아
`config.js`에 넣어야 합니다.

1. [Google Cloud Console](https://console.cloud.google.com/)에서 새 프로젝트를 만듭니다.
2. **API 및 서비스 > 라이브러리**에서 **Google Drive API**를 검색해 사용 설정(Enable)합니다.
3. **API 및 서비스 > OAuth 동의 화면**을 구성합니다.
   - User Type: 외부(External)
   - 앱을 게시(Publish)하지 않고 "테스트" 상태로 두어도 됩니다. 이 경우 **테스트 사용자**에 본인 구글 계정을 등록해야 로그인할 수 있습니다.
   - 범위(Scopes)에 `.../auth/drive.readonly` 외에 `.../auth/userinfo.email`도 추가해주세요
     (로그인한 계정이 소유자 계정인지 판별해 하위 폴더 표시 여부를 결정하는 데 사용됩니다).
4. **API 및 서비스 > 사용자 인증 정보 > 사용자 인증 정보 만들기 > OAuth 클라이언트 ID**
   - 애플리케이션 유형: **웹 애플리케이션**
   - **승인된 자바스크립트 원본**에 GitHub Pages 주소를 추가합니다.
     - 예: `https://james0083.github.io` (경로 없이 origin만 등록하면 됩니다)
   - **승인된 리디렉션 URI**에 이 앱의 페이지 주소를 정확히 추가합니다(조용한 자동
     재로그인에 필요합니다 — 아래 "로그인 유지의 한계" 참고). 끝에 슬래시(`/`)까지
     정확히 일치해야 합니다.
     - 예: `https://james0083.github.io/economic-briefing-viewer/`
5. 발급된 클라이언트 ID(`xxxxxxxx.apps.googleusercontent.com` 형식)를 복사합니다.
6. 이 저장소의 [`config.js`](./config.js) 파일을 열어 `CLIENT_ID` 값을 교체합니다.

```js
const CONFIG = {
  CLIENT_ID: '여기에_발급받은_클라이언트_ID',
  FOLDER_ID: '1KIxaeD2vde9-KgsOUefKzqUVGhWyLfze', // 경제시황분석 - Claude 폴더 ID (이미 설정됨)
  OAUTH_SCOPES: 'https://www.googleapis.com/auth/drive.readonly https://www.googleapis.com/auth/userinfo.email',
  OWNER_EMAIL: 'jaewon000830@gmail.com', // 이 계정으로 로그인할 때만 하위 폴더가 표시됨
  OWNER_ONLY_FOLDER_IDS: ['1mWvYywhASMUfkY1OuKCxjE1xAjbpqVqf'], // OWNER_EMAIL에게만 추가로 보여줄 폴더
};
```

`OWNER_ONLY_FOLDER_IDS`에 넣은 폴더는 `FOLDER_ID` 트리 안에 실제로 들어있는지와 무관하게,
`OWNER_EMAIL`로 로그인했을 때만 최상위에 별도 항목으로 추가됩니다. Drive에서 폴더를 다른
위치로 옮겨도 폴더 ID 자체는 바뀌지 않으므로 계속 정상 동작합니다.

⚠️ **중요**: 이 폴더는 다른 계정과 절대 공유하지 마세요. 앱의 이 로직은 화면에만 안 보이게
하는 것일 뿐, 실제 접근 차단은 Google Drive의 공유 권한이 담당합니다 — Drive에서 공유하지
않은 폴더는 다른 계정이 로그인해도 Drive API가 애초에 데이터를 반환하지 않습니다.

`config.js`를 수정한 뒤 `main` 브랜치에 커밋/푸시하면 GitHub Actions 워크플로우가 자동으로
GitHub Pages에 배포합니다.

## 배포 확인

- 저장소 **Settings > Pages**에서 "Build and deployment" 항목의 Source가
  **GitHub Actions**로 설정되어 있는지 확인하세요(워크플로우가 처음 실행되면 자동으로 설정됩니다).
- 배포가 끝나면 `https://james0083.github.io/economic-briefing-viewer/` 에서 접속할 수 있습니다.

## PWA(설치형 앱)

- 모바일 브라우저에서는 "홈 화면에 추가", 데스크톱 크롬/엣지에서는 주소창의 설치 아이콘으로
  설치할 수 있습니다. 설치하면 브라우저 UI 없이 일반 앱처럼 실행됩니다.
- `sw.js`는 정적 파일(HTML/CSS/JS/아이콘)만 캐싱하고, Drive API·Google 로그인·CDN 요청은
  그대로 네트워크로 보냅니다. 매번 네트워크를 먼저 시도하고 실패할 때만(오프라인 등) 캐시된
  버전을 보여주므로, 배포 후 새로고침하면 항상 최신 버전을 받아옵니다.
- 아이콘을 바꾸고 싶으면 `icon-192.png`, `icon-512.png`, `apple-touch-icon.png`을 같은
  이름의 정사각형 PNG로 교체하면 됩니다.

### 안드로이드에서 설치 시 "안전하지 않은 앱" 경고가 뜨는 경우

일부 안드로이드 브라우저(특히 삼성 인터넷)에서 PWA를 "설치"하면, 실제로는 WebAPK라는
설치 파일이 만들어지는데 이 시점에 **Google Play Protect(또는 삼성 자체 보안 검사)**가
"출처를 모르는/설치 이력이 없는 새 앱"이라며 경고를 띄우는 경우가 있습니다.

- 매니페스트(`manifest.json`)는 설치 요건(아이콘 크기·형식, 필수 필드 등)을 확인했을 때
  정상입니다 — 즉 이 경고는 매니페스트가 깨져서 뜨는 게 아닐 가능성이 큽니다.
- 이건 OS/브라우저 쪽의 앱 설치 보안 검사라서, **웹사이트 코드로 이 검사 자체를 끄거나
  건너뛸 방법은 없습니다.** (Play Store에 정식 등록된 앱만 이런 검사를 면제받습니다.)
- 시도해볼 것: **Chrome 브라우저로 같은 페이지에서 설치해보기** — Chrome은 구글이 직접
  운영하는 WebAPK 서명 경로를 쓰기 때문에 삼성 인터넷보다 이런 경고가 덜 뜨는 편입니다.
  Chrome에서도 똑같이 뜨는지 아닌지로 "매니페스트 문제 vs 브라우저별 차이"를 구분할 수
  있습니다.
- 경고 화면에 "그래도 설치"/"무시하고 계속" 같은 우회 옵션이 있다면, 본인이 만든 개인용
  앱이므로 눌러서 진행해도 괜찮습니다.

## 로그인 유지의 한계

브라우저와 Google의 보안 정책상, **완전히 백엔드가 없는 웹앱은 refresh token을 발급받을
수 없습니다.** refresh token은 만료되지 않고 서버에 안전하게 보관되어야 하는데, 정적
사이트에는 그런 안전한 저장소가 없기 때문입니다. 그래서 매번 로그인 없이 "완전히 끊김
없는" 로그인은 구조적으로 불가능합니다.

### 지금 방식: 전체 페이지 리다이렉트

이 앱은 **팝업도 iframe도 아닌, 전체 페이지를 구글로 이동시켰다가 그대로 돌려받는 방식**으로
조용히 액세스 토큰을 재발급받습니다 — 페이지를 다시 열 때, 그리고 API 요청이 401로 실패했을
때. 구글 로그인 세션이 브라우저에 남아있고 이 앱에 대한 동의가 이미 되어있으면, 구글은
화면을 하나도 그리지 않고(`prompt=none`) 토큰을 붙여서 즉시 페이지를 돌려보냅니다 — 짧은
화면 깜빡임 정도로 끝나고 클릭 등 사용자 조작은 필요 없습니다.

- 이 기능이 동작하려면 위 4번 단계에서 **승인된 리디렉션 URI**에 이 앱 페이지의 정확한
  주소를 등록해야 합니다. `config.js`의 `REDIRECT_URI` 값과 콘솔에 등록한 값이 글자
  하나(끝 슬래시 포함)까지 정확히 같아야 합니다. 등록을 빠뜨리거나 값이 다르면
  **"400 오류: redirect_uri_mismatch"라는 구글 자체 오류 페이지**가 뜹니다(우리 앱
  화면이 아니라 구글 화면입니다) — "Google로 로그인" 버튼을 눌렀을 때 이 오류가 뜨면
  `REDIRECT_URI`와 콘솔에 등록한 값을 다시 비교해보세요. 반대로 조용한 자동 재인증
  (`prompt=none`) 시도가 이 오류를 만나면, 화면 전체가 구글 오류 페이지로 넘어갔다가
  아무 동작 없이 남게 됩니다 — 이 경우에도 원인은 같습니다.
- 다음의 경우에는 다시 "Google로 로그인" 버튼을 눌러야 합니다: 브라우저에서 구글 계정을
  로그아웃한 경우, 이 앱에 대한 접근 권한을 [Google 계정 설정](https://myaccount.google.com/permissions)에서
  직접 취소한 경우, 브라우저 데이터(쿠키)를 지운 경우, 시크릿/프라이빗 모드로 열었거나,
  또는 아래에서 설명하는 "테스트" 상태의 7일 만료 제한에 걸린 경우.

### 지금까지 시도했다가 실패한 방식들 (참고용 기록)

1. **`google.accounts.oauth2` 토큰 클라이언트로 페이지 로드시 자동 재인증** — 이 방식은
   사용자 클릭 없이 호출하면 브라우저의 **팝업 차단 정책**에 걸려 매번 조용히 실패했습니다
   (새로고침할 때마다 다시 로그인 버튼을 눌러야 했던 원인).
2. **숨겨진 iframe + `prompt=none`** — 팝업 대신 iframe으로 우회를 시도했는데, Google
   Identity Services(GIS)가 공식적으로 지원하는 방식이 아니고, 구글의 인증 페이지는
   클릭재킹 방지를 위해 **iframe 삽입 자체가 차단**되어 있어서 iframe이 아예 로드되지
   못했던 것으로 보입니다. 역시 매번 조용히(타임아웃 후) 실패했습니다.
3. 현재 방식(전체 페이지 리다이렉트)은 팝업도 iframe도 쓰지 않는 일반적인 페이지 이동이라
   두 차단 정책 어디에도 걸리지 않습니다. Playwright로 URL 구성·토큰 파싱·에러 처리
   로직을 전수 테스트해 정상 동작을 확인했습니다(다만 이 환경은 아웃바운드 네트워크가
   막혀있어 실제 구글 서버·배포된 사이트로 직접 접속해 눈으로 확인하는 건 불가능했습니다
   — 배포 후 실제 새로고침으로 직접 확인해주세요).

### "Google에서 확인하지 않은 앱" 경고와의 관계

이 경고 자체가 조용한 재인증 실패의 직접적인 원인은 아닙니다 — `prompt=none`은 애초에
아무 화면도 그리지 않으므로, 성공하든 실패하든 이 경고가 뜰 일이 없습니다. 다만 OAuth
동의 화면이 **"테스트" 상태**인 것과는 관련이 있습니다:

- Google 정책상 "테스트" 상태 앱에 발급된 토큰/동의는 **7일 후 강제로 만료**됩니다
  (프로덕션 상태 앱에는 이 제한이 없습니다).
- 이 앱은 `drive.readonly`(민감 범위)와 `userinfo.email`(비민감 범위)만 요청하고
  사용자가 100명 미만이므로, Google의 공식 검증 심사 없이도 "프로덕션"으로 게시할 수
  있습니다. 검증을 받지 않으면 "확인되지 않은 앱" 경고는 계속 뜨지만(최초 동의 시
  "고급 > 이동(안전하지 않음)" 클릭 필요), 7일 만료 제한은 사라집니다.
- **권장**: Google Cloud Console → OAuth 동의 화면(또는 Google Auth Platform) →
  잠재고객(Audience) → **"프로덕션으로 게시"** 클릭. 검증 심사 신청까지는 필요 없습니다.
  이렇게 하면 7일마다 강제로 재로그인해야 하는 문제가 사라집니다.

## 새 사용자(뷰어) 추가하기

이 앱을 다른 사람도 쓸 수 있게 하려면 **두 곳**에 각각 등록해야 합니다. 둘 중 하나만
해서는 동작하지 않습니다 — OAuth 쪽은 "앱에 로그인할 수 있는지"를, Drive 쪽은 "로그인한
계정이 실제로 파일을 볼 수 있는지"를 독립적으로 결정하기 때문입니다.

### 1) Google Cloud Console — 로그인 허용

OAuth 동의 화면이 아직 "테스트" 상태라면(위 "Google에서 확인하지 않은 앱" 항목 참고),
등록된 테스트 사용자만 로그인할 수 있습니다.

1. Google Cloud Console → **API 및 서비스 > OAuth 동의 화면**(또는 **Google Auth
   Platform > 잠재고객(Audience)**)
2. **테스트 사용자** 목록에서 **+ ADD USERS**
3. 추가하려는 사람의 구글 계정 이메일 입력 후 저장

(앞서 권장한 대로 "프로덕션"으로 게시했다면 이 단계는 필요 없습니다 — 아무 구글
계정이나 로그인은 할 수 있게 됩니다. 다만 실제로 뭘 볼 수 있는지는 여전히 2번 단계로
결정됩니다.)

### 2) Google Drive — 실제 파일 접근 권한 부여

1. Google Drive에서 **"경제시황분석 - Claude"** 폴더를 우클릭 → **공유**
2. 추가하려는 사람의 이메일 입력, 권한은 **뷰어(읽기 전용)**로 설정 → 전송

이렇게 하면 그 사람은 로그인 후 최상위 폴더의 `.md` 파일들을 볼 수 있습니다.

⚠️ **"유재원 개인 투자전략 브리핑" 폴더는 절대 공유하지 마세요.** 이 폴더는
`config.js`의 `OWNER_ONLY_FOLDER_IDS`에 등록되어 있어 `OWNER_EMAIL`
(jaewon000830@gmail.com) 계정으로 로그인했을 때만 앱 화면에 표시되는데, 이 화면 제한은
Drive 공유 여부와 무관하게 앱 코드가 하는 일일 뿐입니다. **실제 차단은 Drive의 공유
설정 자체입니다** — 이 폴더를 다른 계정과 공유하면 그 계정은 Drive 웹사이트에서 직접
열어볼 수 있게 되어, 앱에서 숨겨봤자 소용없습니다.

## GitHub 저장소를 비공개로 바꾸면?

**결론: Free 플랜에서는 비공개 저장소로 GitHub Pages를 쓸 수 없습니다.**

- GitHub Pages를 **비공개(private) 저장소**에서 배포하려면 **GitHub Pro**(개인, 유료)
  또는 조직의 **Team/Enterprise** 플랜이 필요합니다. 무료(Free) 플랜은 공개 저장소에서만
  Pages를 켤 수 있습니다.
- Pro/Team으로 비공개 저장소에서 Pages를 켜더라도, **배포된 사이트 자체(웹페이지)는
  여전히 같은 `github.io` 주소로 누구나 접속할 수 있습니다.** 비공개가 되는 건 "소스
  코드 저장소"뿐이고, 빌드된 정적 페이지는 원래부터 인터넷에 공개되는 것이 GitHub
  Pages의 기본 동작입니다. (조직 단위 GitHub Enterprise Cloud에는 Pages 접근 자체를
  조직 구성원으로 제한하는 기능이 있지만, 개인 Pro 플랜에는 없습니다.)
- (참고: 이 환경은 아웃바운드 네트워크가 막혀있어 GitHub 공식 문서를 지금 다시 열어
  실시간으로 재확인하지는 못했습니다. 위 내용은 GitHub Pages의 오래되고 안정적인
  공개 문서 기준이며, 최신 요금제 세부사항은 GitHub 공식 페이지에서 다시 한번
  확인해보시는 걸 권장합니다.)

### 그래서 "코드 보호"에는 어떤 의미가 있나

- 저장소를 비공개로 바꾸면 얻는 것: **소스 코드가 GitHub 검색·브라우징에 안 뜨고,
  임의의 사람이 코드를 열람·포크할 수 없게 됩니다.**
- 저장소를 비공개로 바꿔도 얻지 못하는 것: **웹페이지 자체에 대한 접근 제한**입니다
  (URL을 아는 사람은 누구나 페이지를 열 수 있음 — 다만 실제 브리핑 "내용"은 이미
  Google 로그인 + Drive 공유 권한으로 보호되고 있으므로, 페이지 자체가 열리는 것과
  데이터가 보이는 것은 별개입니다).
- `CLIENT_ID`나 Drive 폴더 ID는 코드에 그대로 노출돼 있어도 안전합니다 — `CLIENT_ID`는
  애초에 공개되어도 되는 값이고(승인된 오리진으로만 제한됨), 폴더 ID를 안다고 해서
  Drive 접근 권한이 없는 사람이 내용을 볼 수 있는 건 아닙니다. 그래서 이 저장소를
  공개로 유지해도 보안상 실질적인 위험은 낮습니다.
- 그래도 "그냥 아무나 소스를 못 보게 하고 싶다"는 개인적인 이유라면, GitHub Pro
  (월 4달러 정도)로 업그레이드하고 저장소를 비공개로 바꾸는 것으로 충분합니다 — 이 경우
  에도 배포/도메인 설정은 지금과 똑같이 유지됩니다.
- 페이지 열람 자체까지 막고 싶다면 GitHub Pages만으로는 불가능하고, Cloudflare Access
  같은 별도의 접근 제어 서비스를 앞단에 두어야 하는데, 이건 사실상 "백엔드 없이"라는
  원래 조건과 배치되는 방향이라 권장하지 않습니다. 지금처럼 Google 로그인을 데이터
  접근의 실질적인 관문으로 쓰는 편이 훨씬 간단하고 이미 충분합니다.

## 알려진 제약

- OAuth 동의 화면을 "테스트" 상태로 둔 경우, 등록된 테스트 사용자 계정으로만 로그인할 수 있고
  로그인 세션이 비교적 짧게 만료됩니다(재로그인 필요).
- 일부 브리핑 파일 본문에 이모지가 깨진 문자로 저장된 경우가 있습니다. 원본 파일의 인코딩 문제로,
  필요하면 Drive에서 원본을 다시 저장해 해결할 수 있습니다.
